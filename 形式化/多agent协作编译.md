# 多 Agent 协作编译：可行性评估

> 状态：2026-10-23 评估 | 依赖：[覆盖与算子审计.md](覆盖与算子审计.md) | 结论：**可行，但必须先封闭词汇表**

---

## 一、结论

**技术上可行，且当前已具备两个关键前提。** 但不是"把人手换成 N 个 agent"那么简单——
没有约束的并行会产出 N 种方言，而引擎对未知字段是**静默忽略**的，
最终结果是"看起来编完了、实际一半不生效"。

需要的三个前提：

| # | 前提 | 状态 |
| --- | --- | --- |
| 1 | **投影词汇表封闭**，未知字段直接报错 | ✅ 已实现（检查 A12） |
| 2 | **每个算子可自动对拍**，不依赖人肉算数 | ✅ 已实现（`tools/verify_ops.py`） |
| 3 | **条件能被通用表达** | ❌ 未实现，见 §四 |

---

## 二、为什么这三个前提是硬性的

### 2.1 词汇表不封闭 = N 种方言

实测：当前 299 个算子用了 **31 种** projection 字段，其中 **4 种引擎不认**
（`size_increase`、`conditional_dice`、`bonus_action_attack_type`、`area`）。
其中 `bonus_action_attack_type` 导致「长柄武器大师」的附赠攻击本该是钝击，
实际却沿用了武器类型——**不报错，只是算错**。

单人开发时这类问题还能靠审计发现；N 个 agent 并行时，每个人都会发明自己觉得
合理的字段名，漂移速度会快一个数量级。**A12 检查（拒绝未知字段 + 显式白名单）
是并行化的准入条件，不是优化项。**

### 2.2 不能自动对拍 = 无法验收

手工编译时我是逐条算数字验证的。这个方式无法规模化——10 个 agent 编 170 条，
没有人能手算 170 次。

`tools/verify_ops.py` 的做法：为每个算子构造最小场景，**装上/卸下**各跑一次，
比较期望伤害。

- `CHANGED`（263 条）：数值变化，正常
- `INERT`（13 条）：数值不变，需人工确认
- `ERROR`（0 条）：求值异常，必须修复

**INERT 不是失败**——它把"需要人工确认"的范围从 299 条压缩到 13 条。
实测这 13 条全部可解释：需要特定武器种类（刺剑、长鞭、巨斧）、特定体型、
多职业、骑乘冲刺，或是"主动宣告型"专长（威力攻击、疯狂连击必须由策略显式引用）。

## 三、可并行与不可并行的划分

### 可以并行

| 工作 | 划分方式 | 冲突面 |
| --- | --- | --- |
| 专长编译 | 按 7 个分类切分 | 无——每个算子一个文件，文件名即 id |
| 战技编译 | 按 5 个流派切分 | 无 |
| 法术编译 | 按环阶切分 | 无 |
| 表格结构化 | 按表切分 | 无 |

**冲突面为零**是这个项目适合并行的根本原因：算子是一文件一条，
id 与数据条目一一对应（检查 A10 强制），不存在共享状态。

### 不能并行

| 工作 | 原因 |
| --- | --- |
| 引擎扩展 | 多人同时改 `calculator.py` 必然冲突 |
| 共性机制设计 | "命中后追加攻击"这类机制横跨多个专长，需要单一负责人 |
| 词汇表变更 | 新增 projection 字段必须走统一评审，否则 §2.1 的漂移会重演 |
| 最终验收 | INERT 的人工确认需要一致的判断标准 |

---

## 四、第三个前提：条件的通用表达（未完成）

这是当前最大的结构性缺口。463 条 `needs_ruling` 的原因分布：

| 原因 | 条数 | 占比 |
| --- | ---: | ---: |
| 条件分支 | 189 | 41% |
| 多选一 | 55 | 12% |
| 结构未匹配 | 44 | 10% |
| 伤害公式 / 持续伤害 / 多段伤害 | 77 | 17% |
| 限次使用 | 21 | 5% |
| 其余 | 77 | 15% |

**41% 是条件分支。** 当前条件是**硬编码进各个字段**的：
`gate.requires_rage`、`gate.requires_prior_move`、`gate.mounted`……
每遇到一种新条件就要改引擎。

若要把这 189 条交给 agent 批量处理，需要一套**条件词汇 + 统一的 `conditions` 结构**，
例如：

```jsonc
"conditions": [
  { "when": { "attacker_state": "raging" },  "then": { "extra_dice": [...] } },
  { "when": { "target_hp": "below_half" },   "then": { "damage_mult": 2 } }
]
```

**这一步不做，并行化只能覆盖剩下 59% 的工作量**，而且条件类专长仍然要逐条改引擎。

## 五、建议的分工方案

若能补齐第三个前提，建议这样组织：

1. **一名架构负责人**（不可并行）：维护词汇表、引擎、条件词汇，评审所有新增字段
2. **按分类切分的编译 agent**：每个 agent 负责一个分类，产出算子 JSON
3. **统一验收**：每个 agent 提交前必须跑
   - `python -I 形式化/tools/check_interfaces.py`（A1–A12 全过）
   - `python -I 形式化/tools/verify_ops.py`（无误报 ERROR，INERT 需给理由）
4. **INERT 复核**：由架构负责人按统一标准裁定"这是真无效还是场景不匹配"

**交付物的一致性由工具保证，不靠约定。** 这是并行化能否成立的关键——
一旦依赖"请大家都按这个格式写"，漂移必然发生。

---

## 六、当前不建议并行的部分

在第三个前提完成前，我建议：

- **不要**让 agent 碰 `calculator.py` / `strategy.py`
- **不要**让 agent 新增 projection 字段
- **可以**让 agent 处理"现有词汇表能完整表达"的条目——即
  `needs_ruling` 中原因不含"条件分支""多选一"的那部分

按当前统计，这部分约 **180 条**（结构未匹配 44 + 公式/持续/多段 77 + 其余），
是可以立即并行的安全区。
